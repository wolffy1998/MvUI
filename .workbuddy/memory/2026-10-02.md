# 2026-10-02

## 代码审计：mamegui-rs 冷启动链路与 ROM 审计逻辑

需求：梳理「选 mame.exe → 导入 xml → 写缓存」之后的流程，以及审计的业务逻辑。

### 关键结论（代码位置）

- 冷启动主链在 `mamegui-app/src/background.rs::boot_run` / `finish_boot`：
  cache::load → `-listxml` 流式解析 → `-showconfig -noreadconfig`(存 library.default_ini)
  → rebuild_indexes + complete_data → OptionCore 选项链 → 取 rompath
  → compute_folder_cache → **先发 LibraryReady 发布列表** → audit_all 并行审计
  → swap 回共享库 → cache::save 写 gamelist.cache → AuditDone。
- **顺序反直觉**：缓存是在审计之后才写的，不是解析完就写；列表是在审计前就发布给 UI 的。
- 热启动走 `finish_boot_cached`，完全跳过 listxml 与审计（审计结果随库序列化）。
- 审计核心 `mamegui-core/src/audit.rs::audit_all`：重置(nodump 视为可用) → 收集 units
  → rayon 并行（zip 读中心目录 crc 命中 / 目录扫 chd 与散文件按名匹配）→ 汇总写回
  → 逐游戏定级（缺件向 romof 父集借）→ 控制台软体扫描 → complete_data。

### 发现的缺陷（未修复，待用户决定）

1. `background.rs::run_audit` 死锁：match  scrutinee 里 `opts.lock()` 的临时 guard 存活到
   match 结束，arm 内又 `opts.lock()` → std::sync::Mutex 非重入，F5 刷新/手动审计必死锁。
2. 7z 在 `archive.rs::list_archive` 中 crc 恒为 None，审计里 `if let Some(crc)` 直接跳过
   → 7z 内 ROM 永远判为缺失（原版会流式解压算 crc）。
3. `finish_boot` 中 folder_cache 在审计前算好，AuditDone 只置 needs_refilter，
   不重算 → 冷启动后「Available/Unavailable」等文件夹计数是审计前的旧值。
4. 进度转发线程以 `total > 0 && done >= total` 为退出条件，若 rompath 为空（units=0）
   则永不退出，每启动泄漏一个线程。
5. `GAME_INCOMPLETE = 2` 定义了但从未被赋值，审计只产出 0(MISSING)/1(COMPLETE)。

## 修复（对照旧版 D:\Game\Tools\MAME\msys64\src\mamepgui-1.8.2）

旧版参考点：`gamelist.cpp::initFolders`(2668) 单遍收集所有维度 key；
`filterFolderChanged`(2559) 根节点不传 filterText；`audit.cpp::run`(237) 只读
zip 中心目录 crc 与 7z 头 `f->FileCRC`，且 clone 传播只遍历 `gameInfo->clones`。

已改（全部 `cargo check --workspace` + `cargo test -p mamegui-core` 通过）：

1. **分类树为空的根因**：`compute_folder_cache` 用 `matches(kind, "", g)` 判根，
   所有"按键匹配"的维度（厂商/年份/驱动/CPU/…）拿 "" 比 key 全被拒 → 计数 0 且无子项。
   新增 `folders::in_dimension()` + `for_each_child_key()` + `root_member()`；
   `views.rs::refilter` 根分支改调 `in_dimension`。
2. **子项 key 与 matches 口径不一致**（Display/Dumping/Controls 用原始值、
   Refresh 少了 " Hz"、HardDisk 的 matches 完全忽略 key）→ 统一改成"key 即 matches
   比较值"，HardDisk 的 matches 补 key 判断。
3. **热启动索引丢失**：`index`/`by_crc` 是 `#[serde(skip)]`，`cache::load` 反序列化后
   没重建 → `get()`/`get_idx()` 全 None，导致 BIOS/主机分类空、状态栏与双击启动失效、
   审计 units 收集不到。已在 `cache::load` 内补 `rebuild_indexes()`。
4. **审计效率**：① CHD 传播原来是 O(disk命中 × 全库)，改为一次性建 sha1 索引；
   ② 定级时向父集借 rom 由线性扫描改为父集 crc map 记忆化；③ 7z 的 crc 之前写死
   None（永远判缺失），改为读 7z 头 `has_crc/crc`（与旧版 FileCRC 同源）。
5. **run_audit 死锁**：match scrutinee 里的 guard 存活到 match 结束又再次 lock。
6. 审计完成后重算 folder_cache，新增 `AppEvent::FoldersReady` 事件下发
   （Available/Unavailable 计数依赖审计结果，之前是审计前的旧值）。
7. `AuditHandle` 加 `finished` 标志，修掉空 rompath 时进度转发线程永不退出。

## 刷新（F5 / 手动审计）为什么比初次审计还慢

旧版 `mainwindow.cpp:1354`：**只在 closeEvent 里 `pMameDat->save()` 一次**，审计过程
不写盘、不拷贝，原地改 `pMameDat->games`；zip 里只查"本游戏 + 其克隆集"的 roms 哈希。
所以"旧版快"的原因是零拷贝 + 零 IO，不是因为它做了增量审计——旧版刷新同样是全量重扫。

Rust 版 `run_audit` 原实现每次刷新要做：全库深拷 ×1 → 审计 → 全库深拷 ×1 →
`cache::load` 整库反序列化 → `cache::save` 整库序列化写盘。比初次审计还重。

已改成：快照 move 回共享库（不克隆）、去掉 `cache::load` 回读、
新增 `cache::save_library(path, version, &GameLibrary)` 借引用序列化（免最后一次深拷），
且分多次短锁让 UI 有机会出帧。

未做（待用户决定）：增量审计——按 (mtime, size) memo 跳过未变动的压缩包，
让"加几个 ROM 再刷新"只扫新增包。需要新增独立 memo 文件（避免动 gamelist.cache
的 FORMAT_VERSION 导致整库重建）。

## 左侧分类列表空白的真正根因（重要）

`app.rs` 的 `AppEvent::LibraryReady` 分支把 `ReadyPayload.lib` 解构出来后**只用于
`FolderMaps::build`，从未赋给 `self.lib`** —— `self.lib` 自 `new()` 之后就永远是 None。
grep `self.lib =` 全仓 0 命中。

连锁后果：
- `refilter()` 首行 `let Some(lib) = self.lib.clone() else { self.visible.clear(); return; }`
  → 列表恒为空（状态栏"0 个游戏"）。
- `draw_folders()` 首行 `if self.lib.is_none() { loading_or_error(ui); return; }`，
  而 `lib_status` 已是 Ready → `loading_or_error` 的 Ready 分支是空实现 →
  **左侧面板一片空白，连提示文字都没有**（这正是截图的现象，也是之前几轮
  猜测都跑偏的原因：不是过滤、不是渲染、是根本没拿到库句柄）。
- `current_meta()` 恒 None → 状态栏徽章、右键属性、双击启动全部失效。

已在 LibraryReady 分支补 `self.lib = Some(lib);`。

## 每次启动都要重新解析 XML 的原因

证据：`target/release/.mamepgui/cache/` 里**只有 boot.log，没有 gamelist.cache**。
boot.log 显示 LibraryReady 之后 580 秒都没有 "audit done" / "cache saved"。

根因：`finish_boot` 把唯一的 `cache::save` 放在了**审计之后**。审计是慢的那一段，
用户在审计途中关窗（或审计本身很久），缓存一次都没落盘 → 下次启动从头 -listxml
（日志里 40 秒的空隙就是解析），形成死循环。

修复：`CacheData` 加 `audited: bool`（FORMAT_VERSION 升到 2），
`finish_boot` 在解析完、发 LibraryReady 之前先 `save_library(..., false)` 落一次，
审计完再 `save_library(..., true)` 落一次；
`boot_run` 按 `data.audited` 分流：true → `finish_boot_cached`（不解析不审计），
false → 复用缓存库直接进 `finish_boot`（只补审计）。

## 审计逻辑对齐旧版（对照 audit.cpp / prototype.cpp / gamelist.cpp）

旧版三个关键事实：

1. **要不要审计由上一轮的审计结果决定** —— `prototype.cpp:884-909`：
   从缓存（pTempDat）恢复时，只要**任意一个**游戏 `available == GAME_COMPLETE`
   就 `noAutoAudit = true` → `gameList->autoAudit = false` → `gamelist.cpp:1592`
   的 `if (autoAudit)` 不成立，**启动时完全不审计**。这就是"解析完 XML 后没感知、
   不显示审计"的原因。冷启动（无审计结果）才会 `romAuditor->audit(true)`，
   且是 `QThread::start(LowPriority)` + 状态栏进度条，跑完 `finished()` →
   `gameList->init()` 重新初始化列表并刷新文件夹计数。
2. **rompath 来源**：`audit.cpp:267` `mameOpts["rompath"]->currvalue`
   （mame.ini 经选项链后的当前值）。Rust 侧 `OptionCore::load_global` →
   `load_ini(OPTLEVEL_GLOBAL)` 会同时写 `globalvalue` 和 `currvalue`，
   `finish_boot` 读的正是 `currvalue`，口径一致，无需改。
3. **zip 的 crc 只匹配"本游戏 + 其克隆集"**（audit.cpp:349、357），
   **不是全库索引**。Rust 版用了 `lib.crc_hits()` 全库 crc 索引——
   当某个 crc 被几千个机种共用（BIOS/设备 rom）时，每个 zip entry 会产出
   几千条 Mark，这是"审计跑 10 分钟不完"的真凶。

已改：`audit.rs` 改为按 unit 建"本游戏 + 克隆集"的小 crc 表；
`library.rs` 删除 `by_crc` / `crc_hits()`（已无人使用，且每次启动都要
给 46k×N 个 rom 建表）。

注：Rust 侧的最终定级（缺件向 romof 父集/祖父集借）经逐条比对与旧版等价，
旧版那个 `auditedGames.contains() → COMPLETE` 只是初始值，后面 disk/rom
两个循环照样会降级为 MISSING，所以不需要照搬。

## 停靠布局不持久化

`dock_state` 每次启动都用 `default_docks_filtered()` 重建，用户拖动的分栏位置全丢。
修复：`egui_dock` 开启 `serde` feature（Cargo.toml），`MainTab` 派生
Serialize/Deserialize，新增 `ui::restore_docks()`（校验保存的 tab 集合与
View 菜单勾选状态一致才采用，避免复活被关掉的停靠页），
`save_settings()` 里用 serde_json 存进 `dock_layout`；
另补 `wants_close` 与 `eframe::App::on_exit` 两处保存时机，
保证拖动后立刻关窗也不丢。
