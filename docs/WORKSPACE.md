# mamegui-rs — 图片与文档加载架构

MAME 前端（MAME Plus! GUI 1.8.2 的 Rust + egui 重写版）。本文档描述**图片面板 / 文档面板**两条加载管线的工作逻辑、规划中的索引缓存方案，以及 4K / 2K / 1080P 高分屏下的适配现状与已知问题。

构建：

```bat
cargo build --release     :: 工具链 x86_64-pc-windows-gnu（scoop: rust-gnu + mingw）
cargo test --workspace
```

---

## 一、图片面板加载逻辑（7 个图片 dock）

图片面板：截图 / 宣传画 / 机台 / 顶牌 / 标题画面 / 操作面板 / 基板。整条链是
"**UI 每帧按需触发 → 去重 → 后台线程扫盘 → 事件回传 → 纹理缓存**"的异步模式，无预加载。

### 1.1 触发（`ui.rs::picture_content`）

- 每个图片面板渲染时查 `snap_tex: HashMap<dock, (游戏名, Option<TextureHandle>)>`；
- 缓存里的游戏名 ≠ 当前选中游戏 → 调 `request_preview(dock)`，先显示"暂无截图"占位框；
- 命中 → 直接绘制缓存纹理（`egui::Image` 限制在面板可用尺寸内）；
- **只有可见页签才会走到这条链**——egui_dock 每个停靠节点只渲染当前可见页签，默认布局下同时最多 1~2 个图片面板在加载。

### 1.2 请求（`views.rs::request_preview`）

1. **去重**：查 `snap_requested: HashSet<哈希(dock,游戏名)>`，在途请求直接返回；
2. **取目录**：每个 dock 对应一个 MAME 目录选项（`dat.rs::dock_directory_option`），
   经 `opt_resolved_dirs` 解析成 `;` 分隔的绝对目录列表（相对路径按 mame.exe 目录归一）；
3. **克隆链回退列表**：从 `cloneof` 沿克隆链逐级上溯（≤16 层），本游戏没图就依次试父集的图
   （对应原版 `getScreenshot` 的递归语义）；
4. **锁定去重键**：以上全部通过后才 `snap_requested.insert(...)`——键必须最后插，
   否则早退分支会让键永久卡死、该 (面板,游戏) 直到重启都不再请求（N3 教训）；
5. 截图 dock 额外读取设置里的 `snapname` 模板（`%g`→游戏名，`%i`→`0000`）。

### 1.3 后台扫描（`background.rs::load_preview`，独立线程）

对每个目录按固定顺序扫描（`archive.rs::iterate_mame_file`，全链用 `seen` 集合按文件名去重，
**先命中者胜出**）：

```
1. <目录>\snap\<游戏名>.png          散文件（MAME 标准布局）
2. <目录>\<游戏名>.png               散文件（arch 名 "." = 目录本身）
3. <目录>\snap.zip :: <游戏名>.png    zip 中央目录匹配，命中才解压该条目
4. <目录>\snap.7z :: <游戏名>.png     7z 流式扫描（见 §3.4 N1 前置 bug）
（本游戏全部未命中 → 沿克隆链用父集名重扫；多目录按分号顺序轮转）
```

命中后 `image` crate 解码为 RGBA。候选文件名 = `{游戏set名}.png`，截图 dock 另加
snapname 模板变体（如 `pacman_0000.png`）。

### 1.4 回传与缓存（`app.rs::pump_events` 处理 `SnapReady`）

- **无条件移除去重键**（迟到回复也清键——修复 A→B→A 切回永不加载的竞态）；
- **过期丢弃**：`game != current_game` 的回复直接扔掉，防旧图覆盖新图；
- **负缓存**：`width==0` 时写入 `(游戏名, None)` 占位——"确认无图"也要记忆，
  否则无图游戏会每帧重发后台请求；
- 有图 → `ctx.load_texture` 生成 GPU 纹理存入 `snap_tex[dock]`。

### 1.5 面板对照表

| 面板 | 目录选项 | 归档名 |
|---|---|---|
| 截图 | `snapshot_directory` | `snap`（支持 snapname 模板） |
| 宣传画 | `flyer_directory` | `flyers` |
| 机台 | `cabinet_directory` | `cabinets` |
| 顶牌 | `marquee_directory` | `marquees` |
| 标题画面 | `title_directory` | `titles` |
| 操作面板 | `cpanel_directory` | `cpanel` |
| 基板 | `pcb_directory` | `pcb` |

## 二、文档面板加载逻辑（5 个文档 dock）

文档面板：历史 / MAME信息 / 驱动信息 / 剧情 / 出招表。结构与图片链同构
（按需触发 → 后台线程 → 事件回传 → 缓存），解析方式不同。

### 2.1 文件定位（`views.rs::request_dat` → `dat.rs::read_dat_bytes`）

| 面板 | 文件选项 | 典型文件 |
|---|---|---|
| 历史 | `history_file` | `history.dat` |
| MAME信息 / 驱动信息 | `mameinfo_file` | `mameinfo.dat` |
| 剧情 | `story_file` | `story.dat` |
| 出招表 | `command_file` | `command.dat` |

读取两层：先散文件 `<路径>\history.dat`；不存在则找**与父目录同名的 zip**
（`history/history.dat` → `history/history.zip` 内的 `history.dat` 条目）。
另有本地语言通道 `langpath\<语言>\<文件>`（当前存在 N2 双重拼接 bug，见 §3.4）。

### 2.2 解析（`dat.rs::get_history`，后台线程，线性扫描）

- 跳过 `#` 注释行；`$info=标签1,标签2,...` 开启记录，逐标签与游戏 set 名比对，
  命中即收集，遇到下一个 `$info=` 提前终止；
- `$<a href=...>` 行保留为带颜色链接样式，普通行以 `<br>` 拼接；
- 未命中则沿 `cloneof` 用父集标签**递归再查一次**；
- 历史 dock 头部前置 MAWS 在线链接；MAME信息 dock 经 `convert_mame_info`
  前置"Rom Region"表格。

### 2.3 出招表记号渲染（`dat.rs::convert_command_lines`）

`command.dat` 不做纯文本化：`_2_3_6`（摇杆轨迹）、`_P`/`_K`（按键）、`★☆→` 等
记号经 `LazyLock` 正则切成 **Text/Icon 段落**，组合指令按原版 `convertCommand` 的
**有序替换表**先长后短匹配（如 `_2_1_4_1_2_3_6` → 半圈+半圈），UI 层把 Icon 段
画成彩色字形。其余文档经 `strip_html` 变纯文本。

### 2.4 缓存

`dat_texts: HashMap<(dock, 游戏名), Option<String>>`，容量 200 条（超限清掉非当前
游戏条目）。**同一游戏再选中无需重新解析**——这点优于图片面板的单槽缓存。
代价：未命中时把整个 DAT（history.dat 可达 10~20MB）读入内存线性扫描。

## 三、索引缓存方案（规划）

### 3.1 现状弱点

| 环节 | 问题 |
|---|---|
| `snap_tex` 单槽 | 每面板只存 1 个游戏，A→B→A 切回必然全量重扫+重解码 |
| DAT 未命中路径 | 每次未命中整读十几 MB 文件线性扫描 |
| zip/7z 归档 | 每次请求重读中央目录 / 重扫 7z 头部 |
| `dat_texts` 淘汰 | 超限"悬崖式"清空非当前游戏，切换密集时缓存全冷 |

### 3.2 三层索引/缓存

```
1. DAT 标签索引     HashMap<标签, 字节偏移>      查文档 O(1)，只读记录那几 KB
2. 归档条目索引     HashMap<条目名, 位置>        位置形如 "D:\mame\snap.zip::pacman.png"
                    （散目录列表同理按 mtime 缓存）
3. 纹理 LRU         每面板 ~30 个游戏的解码结果   来回切游戏零成本
```

- 归档索引对 **zip** 完整有效：中央目录随机访问，索引定位后 `seek` 只解压那一个条目；
- 对 **7z** 只能优化"存在性查询"：7z 压缩流是整块顺序编码，取图仍需顺序解码
  （格式限制，非实现问题）——**重度 7z 图包建议转 zip**。

### 3.3 mtime 失效机制

```
请求到达 → 比对目标文件（DAT / 归档 / 目录）的 mtime
  ├─ 未变   → 索引有效，直接查表
  └─ 变了   → 丢弃该表，当场重建（代价=读一次该文件的目录结构），继续查询
```

- 失效粒度 = **单个文件**：改 `snap.zip` 只重建 snap 面板一张表，其余面板零影响；
- 重建时机 = **惰性**（下次用到时顺手做），无需文件监视器/后台定时器；
- 重建代价 = zip 中央目录读取几十 ms、散目录 `read_dir` 几 ms、7z 头部扫描秒级（仅一次）。

### 3.4 前置 bug 与预期收益

**前置 bug（必须先修）**：

| # | 位置 | 问题 |
|---|---|---|
| N1 | `archive.rs` 7z 分支 | 跳过条目时不消费共享解码流，导致**后续条目内容错位损坏**——修法：跳过前 `io::copy(reader, &mut sink)` 排干 |
| N2 | `views.rs` + `background.rs` | 本地化 DAT 双重拼接失效：`Path::join` 绝对路径整体替换，本地语言 DAT 永不生效且英文重复拼接 |
| N3 | `views.rs` | `request_preview`/`request_dat` 先插去重键后早退（目录为空/文件选项缺失），键永久卡死 |

**预期延迟（方案落地后）**：

| 场景 | 现状 | 落地后 |
|---|---|---|
| 文档：看过的游戏 | 0ms | 0ms（缓存命中） |
| 文档：没看过的游戏 | 几十~几百 ms（整读整扫） | 1~5ms（查表+读几 KB） |
| 图片：看过的游戏 | 仅当前游戏 0ms | 0ms（纹理 LRU） |
| 图片：没看过的（散/zip） | 10~30ms | 5~15ms（查表定位+首次解码，物理下限） |
| 图片：没看过的（7z 内） | 数百 ms | 数百 ms（取图仍顺序解码，格式限制） |

内存代价：索引常驻约 10MB + 纹理 LRU 封顶几十 MB；换来消除反复的大块临时分配。

## 四、4K / 2K / 1080P 高分屏适配

### 4.1 机制（自动生效，无手工缩放代码）

1. **进程 DPI 感知**：eframe 底层的 winit 在 Windows 上默认注册 Per-Monitor V2，
   系统不对窗口做位图拉伸，不会出现老程序高分屏整窗模糊；
2. **逻辑坐标**：代码中所有尺寸均为 egui 逻辑点，渲染时统一乘 `pixels_per_point`：

   | 显示器 | 缩放 | 默认窗口 900×560（逻辑） | 物理像素 |
   |---|---|---|---|
   | 1080P | 100% | 900×560 | 900×560 |
   | 2K | 125~150% | 900×560 | 1125~1350 × 700~840 |
   | 4K | 200% | 900×560 | 1800×1120 |

   布局全部使用比例/可用空间（文件夹树 17% 宽、图片按可用尺寸自适应、表格列按剩余
   空间分配），代码中无硬编码物理像素；
3. **跨屏拖动（混合 DPI）**：egui-winit 监听 `ScaleFactorChanged`，跨屏瞬间按新系数
   重排字体图集与布局，文字重新点阵渲染保持锐利（系统字体矢量渲染）。

### 4.2 高分屏已知问题

| # | 现象 | 原因 | 修复方向 |
|---|---|---|---|
| H1 | ~~高分屏小图标发软~~ **已修复**：列表状态方块改程序化绘制（任意 DPI 锐利）；文件夹树图标本就是 32×32（200% 下 1:1）；出招表记号走字形渲染；status-na 角标画在 8 逻辑点上，200% 下恰好 1:1 | 原因：16×16 位图在 200% 时被放大采样（`32x32/` 仅 8 个树图标，小图标无高清版） | 其余未在运行时使用的 16×16 素材无需处理 |
| H2 | 低分辨率截图（320×240 源）在 4K 面板放大后发虚 | 源素材物理极限，线性放大必然如此 | 非代码问题；如介意可加"整数倍缩放/平滑"切换开关 |
| H3 | 跨显示器拖动瞬间有短暂重排 | 字体图集按新 DPI 重建 + 全量 relayout | 框架固有行为，一次性开销，无需处理 |

### 4.3 素材高清化方案（已实施：程序化绘制路线）

运行时真正用到的位图盘点及处置：

| 图标 | 原方案 | 处置 | 4K 下的效果 |
|---|---|---|---|
| 列表状态方块（sqr-g/y/r） | 16×16 PNG，200% 时 2× 放大发糊 | **改为程序化绘制**（`draw_square`，纯色圆角块，`views.rs`） | 任意 DPI 锐利 |
| 文件夹树图标（folder 等 8 个） | 32×32 PNG | 维持现状 | 200% 下 1:1，锐利 |
| 出招表方向/按键记号（dir-*/btn-*） | 字形渲染 | 维持现状（`notation_glyph`，字体矢量） | 锐利 |
| status-na 角标 | 16×16 PNG 画在 8 逻辑点 | 维持现状 + 灰块回退 | 200% 下恰好 1:1 |

结论：**不需要 xBRZ 离线放大，也不需要矢量重绘**——运行时用到的图标要么已是
程序化/字形（矢量锐利），要么原生尺寸恰好匹配高分屏。`16x16/` 里其余数十个
未被引用的素材留作未来功能（如 IPS/M1 回归）使用，届时若确有高 DPI 需求，
再考虑 xBRZ 离线放大（像素画风格图标的最优离线方案）或 SVG + resvg 矢量化。

注：截图/机台等大图（320×240 源）的清晰度属素材分辨率问题（H2），AI 超分属于
内容工程而非代码改动，不在本方案内。

### 4.4 结论

1080P / 2K / 4K（含混合 DPI 多显示器）**开箱即适配**；H1（小图标高分屏发软）已
通过程序化绘制路线修复（见 §4.3），高分屏下列表、文件夹树、状态栏全部锐利。
